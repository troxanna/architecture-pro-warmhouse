# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление устройствами**
В системе реализованы операции управления устройствами (создание/редактирование/удаление) на уровне API. При этом в задании не определены акторы и интерфейсы, которые используют эти операции (UI/админ-панель/интеграция). Поэтому в рамках As-Is управление записями об устройствах рассматривается как техническая возможность системы, а процесс наполнения данных — как внешний/неописанный.


**Ууправление отоплением**

1. Пользователь может отправлять команды на включение или выключение отопления.
2. Пользователь может просматривать актуальный статус отопления в доме (вкл/выкл)

1. Система поддерживает выполнение команд на включение и выключение отопления;
2. Система поддерживает хранение данных об устройствах (реле).

**Просмотр текущей температуры**

1. Пользователь может просматривать температуру со всех датчиков, установленных в доме

1. Система поддерживает получение данных о температуре от внешней системы;
2. Система поддерживает хранение данных об устройствах (датчики).

### 2. Анализ архитектуры монолитного приложения

**Архитектурный стиль и ключевые компоненты**

- **Тип архитектуры:** монолитное приложение  
- **Язык программирования:** Go  
- **База данных:** PostgreSQL  
- **Потребитель системы:** пользователь, взаимодействующий через веб-интерфейс  

**Интеграции**

- В рамках требований система предполагает взаимодействие с датчиками температуры и реле отопления через их внешние интерфейсы (API).
- Все обращения к устройствам:
  - инициируются системой;
  - выполняются синхронно;
  - используют заранее известные данные, необходимые для обращения к внешним интерфейсам устройств.
- Устройства:
    - не инициируют взаимодействие;
    - не отправляют данные самостоятельно;
    - отвечают только на запросы системы.

**Архитектурные допущения и неопределенности (As-Is)**

- В текущей реализации системы отсутствуют сущности и бизнес-логика, связанные с управлением пользователями и домами. Привязка устройств к пользователю или дому не реализована и рассматривается как внешняя по отношению к системе предпосылка.
- Система содержит API для управления записями устройств в собственной БД. При этом сценарии и роли, инициирующие создание и привязку устройства, в задании не описаны. В As-Is принимается допущение, что регистрация устройств выполняется внешним по отношению к основным пользовательским сценариям процессом.
- В предоставленных материалах отсутствует кодовая реализация функционала управления отоплением, включая модели реле отопления, API управления и интеграцию с внешними сервисами устройств. В рамках As-Is данная функциональность фиксируется как заявленная на уровне требований, но не реализованная в текущей кодовой базе.

### 3. Определение доменов и границы контекстов

#### Вводные допущения
В рамках As-Is описание доменов отражает функциональность, заявленную в требованиях, включая управление отоплением, часть которой на текущий момент не имеет реализации в кодовой базе.

#### Домены

- **Домен «Управление устройствами дома»**
Домен отвечает за управление жизненным циклом и конфигурацией устройств, подключённых к дому пользователя.

- **Домен «Мониторинг температуры»**
Домен отвечает за получение текущей температуры и отображение её пользователю.

#### Границы контекстов

**Device Management Context**
Управление жизненным циклом устройств и их параметрами.

Внутри контекста:
- бизнес-логика выполнения команд управления;
- бизнес-логика добавления и удаления устройств;
- бизнес-логика изменения параметров устройств;
- хранение и обновление настроек устройств;
- синхронное взаимодействие с Home Devices API;
- обработка результата вызова;
- отображение результата пользователю.

**Temperature Monitoring Context**
Реализация сценария получения и отображения температуры.

Внутри контекста:
- запрос температуры;
- синхронное взаимодействие с Home Devices API;
- обработка результата вызова;
- отображение температуры пользователю.

### **4. Проблемы монолитного решения**

- **Ограниченная масштабируемость монолита**
    - монолитное приложение сложно масштабировать по отдельным функциям (например, отдельно управление отоплением и отдельно опрос температуры);
    - рост числа домов и устройств приводит к росту нагрузки на один сервис.

- **Синхронное взаимодействие и опрос устройств**
    - сервер синхронно опрашивает датчики, что при большом количестве домов становится узким местом;
    - задержки и таймауты при недоступности устройств напрямую влияют на отклик системы.

- **Единая точка отказа**
    - сбой монолитного приложения приводит к полной недоступности управления и мониторинга;
    - проблемы с базой данных останавливают работу всей системы.

- **Сложное и “дорогое” развертывание**
    - обновление системы требует остановки и перезапуска всего приложения;
    - возрастает риск простоя и затрудняется частый выпуск изменений.

- **Низкая гибкость под новые бизнес-цели**
    - система изначально спроектирована только для управления отоплением и мониторинга температуры;
    - расширение в сторону экосистемы умных устройств увеличит сложность и связанность кода монолита.

- **Зависимость от выездов специалистов**
    - подключение устройств невозможно без участия специалиста;
    - такой процесс плохо масштабируется организационно и финансово.

- **Отсутствие событийной модели**
    - устройства не инициируют взаимодействие и не отправляют данные самостоятельно;
    - отсутствие push-механизмов и событий усложняет реализацию автоматики и реакций в реальном времени.

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия микросервисов в экосистеме WarmHome используются два типа API:
- REST API — для синхронных запросов, когда вызывающему сервису нужен ответ сразу. Эти операции пользовательского интерфейса требуют немедленного ответа и хорошо ложатся на CRUD-операции с понятными HTTP-кодами и контрактами.
- AsyncAPI (события в брокере сообщений) — для асинхронного взаимодействия, когда процессы распределённые, могут выполняться долго и не требуют мгновенного ответа (устройства могут быть офлайн, доставка может занимать время).
